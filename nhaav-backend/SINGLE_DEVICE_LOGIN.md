# One device per login

An account may use NHA AV from **one device at a time**. The same email and
password work everywhere, but they cannot hold two live sessions: the second
device is challenged, and only the human can decide to take the session over.

## What the user experiences

1. Normal login on device A — bound silently, nothing to answer.
2. Login on device B with the same credentials — the login page asks which
   device keeps the session, with one button per outcome:

   > **Already signed in on another device**
   > This account is signed in on *Chrome on Windows* (since …). Nhaav allows
   > one device at a time, so choose which device keeps the session.
   >
   > `Stay in this device` — Signs *Chrome on Windows* out and uses *Safari on iOS*.
   > `Switch to another device` — Keeps *Chrome on Windows* signed in; you will not be signed in here.

   Choosing *Switch to another device* changes nothing and says so: "Nothing
   changed — this account stays signed in on …".

3. Confirming hands the session to device B. Device A's next request gets a
   **401** ("This session was moved to another device…"), the app clears its
   state and returns it to the login screen with that message.
4. Logging out releases the device, so the next login from anywhere is
   unchallenged — logging out is the deliberate way to move devices.

## Rules and non-rules

| Question | Answer |
|----------|--------|
| Does switching devices consume an extra access pass? | **No.** The live pass moves with the session and its 6-hour clock keeps running. |
| Does the existing 6-hour timer restart? | **No.** Same pass, same `expires_at`. |
| From when does the rule apply? | From the account's first login, for every non-admin role — including locked (pre-approval / pre-subscription) accounts. |
| Are admins device-locked? | No. Admins are platform staff (same exemption as the marketplace gate). |
| What about a client that sends no device id (curl, scripts)? | Unchanged behaviour: nothing is bound and nothing is challenged. |

## Where it lives

| Piece | Location |
|-------|----------|
| The rule | `app/services/device_session_service.py` |
| Binding on login (and the 409 challenge) | `app/services/auth_service.py::login_user` (`claim`) |
| Per-request enforcement | `app/middleware/auth_guard.py` (`assert_request_device`, both guards) |
| Releasing the device | `POST /auth/logout` (`release`) |
| Stored on | `users.active_device_id` / `active_device_label` / `active_device_at` (migration `d7e8f9a0b1c2`) |
| Client identity | `nhaav-frontend/src/services/device.ts` (id in `localStorage`, `X-Device-Id` on every request) |
| The prompt (`Stay in this device` / `Switch to another device`) | `nhaav-frontend/src/components/LoginForm.tsx` + `useLoginForm` |

### What this is not

The device id is generated by the browser: it is an **entitlement boundary, not
a credential**. It never replaces the JWT and it is not a defence against a
stolen token — a determined attacker can spoof the header. What it does
guarantee is the product rule: one account, one live session, and the human is
always asked before the first session is taken away.

## Verifying it

```bash
cd nhaav-backend
.venv/Scripts/python.exe -m pytest tests/test_single_device_login.py -q
```

That suite pins: the first login binds, the same device is never challenged, a
second device gets 409 `device_conflict`, confirming moves the session and the
displaced device is 401 afterwards, the pass and its countdown are untouched,
logout releases the device, device-less clients are unaffected, and admins are
exempt.
